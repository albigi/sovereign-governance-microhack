## Applicability result

`python tools/gspp/applicability.py --profile <id>` writes `tools/gspp/out/applicability-<id>.json` (format: `schemas/applicability.schema.json`). Every requirement in the mapping appears with `id`, `applicable` and `reason`; applicable ones also carry their candidate controls and `policy_coverage`: `full`, `partial` or `none` (no Azure Policy definition fits). Challenges 2 to 4 read this file. The rule:

1. The profile must satisfy its archetype's constraints.
2. An elevated-level requirement applies only when the protection need is high.
3. Every `applies_when` condition must hold for the profile.
4. Candidate controls are kept when they fit the application's resource types and archetype.

## Upgrade the catalogue

The BSI Grundschutz++ catalogue is published at [BSI-Bund/Stand-der-Technik-Bibliothek](https://github.com/BSI-Bund/Stand-der-Technik-Bibliothek) ([BSI's Grundschutz++ page](https://www.bsi.bund.de/DE/Themen/Unternehmen-und-Organisationen/Standards-und-Zertifizierung/Grundschutz-in-der-Informationssicherheit/Grundschutz-Plus-Plus/grundschutz-plus-plus_node.html)). The kit never follows "latest": it downloads one pinned commit and refuses a file whose SHA-256 differs.

**Where to configure it.** The `catalogue` block of [`catalogue-mapping.json`](catalogue-mapping.json) is the only place. `tools/gspp/extract.py`, `tools/gspp/check_ids.py` and `tools/oscal/build_component.py` all read it; do not copy its values anywhere else.

| Field | Meaning |
|---|---|
| `repository` | `https://github.com/<owner>/<repository>`; only github.com is fetched |
| `path` | Catalogue file inside the repository |
| `revision` | Full 40-character commit hash, never a branch or tag |
| `sha256` | SHA-256 of that file |
| `oscal_version`, `last_modified` | Descriptive; `extract.py` rejects values that contradict the downloaded file |

**Upgrade steps.** Do them in one reviewed pull request.

1. Find the commit to adopt: browse the repository, or `gh api "repos/BSI-Bund/Stand-der-Technik-Bibliothek/commits?path=control_layer/Grundschutz%2B%2B/Grundschutz%2B%2B-resolved_catalog.json&per_page=1" --jq '.[0].sha'`.
2. `python tools/gspp/extract.py --pin <commit>` downloads that commit, parses it, writes nothing and prints `revision`, `sha256`, `oscal_version` and `last_modified`. Copy them into the `catalogue` block. Read what changed in the release notes of the repository before you trust it.
3. `python tools/gspp/extract.py` downloads at the new pin and writes the local extract.
4. `python tools/gspp/check_ids.py` and `python tools/gspp/applicability.py --all`. A removed or renamed ID, or a changed modal verb or security level, fails here: update the mapping (`id`, `modal_verb`, `security_level`) and review whether the route and candidate controls still fit. `check_ids.py` also refuses an extract built from another pin.
5. `python tools/oscal/build_component.py`, then `--check`, then `python tools/oscal/validate.py` regenerate and validate the Azure component, whose back-matter link and hash follow the pin.
6. Run the unit tests (`python -m unittest` in each `tools/` subfolder that has tests), refresh the expected output in the [challenge 1 solution](../walkthrough/challenge-01/solution-01.md) if the control count changed, and describe the change in the pull request.

**The enforcement layer follows automatically.** `tools/doctrine/doctrine.py` reads `repository`, `path`, `revision` and `sha256` from this block too; `doctrine.json` holds no copy and is refused if it does. After the steps above, run `python tools/doctrine/doctrine.py generate` to write the new commit into the policy set as `catalogueCommit`, then `python tools/doctrine/doctrine.py check --catalogue tools/gspp/out/gspp-extract.csv`. Until you regenerate, `check` reports the policy set as stale; with the extract, it also refuses one built from another pin and compares the doctrine's IDs, verbs and levels with the catalogue.

`--input <file>` (a mirror or an offline copy) is still checked against the configured digest. A catalogue hosted elsewhere than github.com needs a change to `extract.py`.

## Check before you commit

```bash
python tools/gspp/check_ids.py           # IDs, verbs and levels match the pinned catalogue; no catalogue text in the kit
python tools/oscal/build_component.py --check
python tools/oscal/validate.py           # needs: python -m pip install -r tools/oscal/requirements.txt
python tools/doctrine/doctrine.py check  # doctrine invariants, generated files current, agreement with the catalogue mapping
```

## Rules for this folder

- **IDs and own mappings only.** No BSI catalogue text and no generated extracts; the catalogue is downloaded at run time by `tools/gspp/extract.py`.
- **Candidate, not compliance.** Every mapping is a candidate until an information-security expert has reviewed it.
- **Versioned.** A schema change carries a new version and is described in its pull request, so importers can adapt.
